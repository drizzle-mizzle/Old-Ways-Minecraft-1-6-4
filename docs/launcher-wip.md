# Лаунчер W-Factory — рабочие заметки

> Черновик. Решения по стеку приняты, код самого лаунчера ещё не начат.
> Готовы и проверены три вещи: патчер джарников (`tools/patch_jars.py`),
> зеркало набора запуска (`tools/fetch_client.py`) и сервис авторизации
> со скинами (`auth/`). Между собой они пока не связаны — не выбран домен.

## Задача

Свой лаунчер: авторизация через наши аккаунты, скины, привязанные к аккаунту,
автообновление сборки, вшитые ресурспаки и моды. Позже — сайт для управления
аккаунтами, откуда лаунчер и скачивается.

Целевые системы: Windows 7 / 10 / 11 и Ubuntu 20.04+. Минимум телодвижений
у пользователя — скачал, поставил, играет.

## Главная находка

**В 1.6.4 нет authlib.** Клиент и сервер ходят за авторизацией и текстурами
по обычному HTTP на адреса, зашитые в байткод строковыми константами.
Ни подписей текстур, ни проверки ключей, ни UUID. Вся поверхность:

| Где | Класс | Константа |
|---|---|---|
| клиент | `bcw.class` | `http://session.minecraft.net/game/joinserver.jsp?user=` |
| клиент | `beu.class` | `http://skins.minecraft.net/MinecraftSkins/%s.png` |
| клиент | `beu.class` | `http://skins.minecraft.net/MinecraftCloaks/%s.png` |
| клиент | `jz.class` | `http://session.minecraft.net/game/checkserver.jsp?user=` (встроенный сервер) |
| сервер | `net/minecraft/server/v1_6_R3/ThreadLoginVerifier.class` | `http://session.minecraft.net/game/checkserver.jsp?user=` |

Аргументы запуска тоже простые: `--username X --session Y`, без accessToken.

То есть самая тяжёлая часть современных лаунчеров здесь почти отсутствует.
Побочный эффект: после переезда на свою авторизацию можно вернуть
`online-mode=true`, и сервер начнёт проверять игроков через наш сервис вместо
мёртвого мояновского — дыра «любой заходит под любым ником» закрывается.

## Почему не берём готовое

| Проект | Лицензия | Что даёт | Почему мимо |
|---|---|---|---|
| [GravitLauncher](https://github.com/GravitLauncher/Launcher) | GPL-3.0 | Авторизация, скины, обновления, сборки | Официально 1.7.10–1.20 |
| [Helios Launcher](https://github.com/dscalzi/HeliosLauncher) | MIT | Electron-оболочка, манифест раздачи, апдейтер | Авторизация под Mojang/Microsoft |
| authlib-injector, Drasl, Ely.by | open | Свой Yggdrasil | Требуют authlib, а он с 1.7.2 |

Граница экосистемы проходит по 1.7.10 — там Mojang ввела authlib и UUID.
Бэкпорт чужой архитектуры под 1.6.4 дороже, чем написать тонкий слой самим:
у нас на всю авторизацию четыре строки.

У Helios стоит позаимствовать формат манифеста раздачи и логику апдейтера —
лицензия MIT позволяет.

## Стек лаунчера

| | | Почему |
|---|---|---|
| Язык и UI | Java 8, Swing + [FlatLaf](https://github.com/JFormDesigner/FlatLaf) | В Temurin 8 JRE нет JavaFX (`jfxrt.jar` отсутствует), Swing есть всегда. FlatLaf — Apache-2.0, требует Java 8+, живой |
| Рантайм | Temurin 8u504 JRE, один на лаунчер и на игру | Игра требует Java 8 в любом случае. Пишем лаунчер на ней же — второй рантайм не нужен |
| Windows | Инсталлятор Inno Setup | Работает на 7/10/11 |
| Linux | tar.gz с `run.sh` | Сборки Temurin 8 собраны под старую glibc, Ubuntu 20.04 проходит |

Размеры: Windows x64 JRE 40,1 МБ, Linux x64 41,8 МБ — одна и та же версия.

**Electron и Tauri отпали из-за Windows 7.** Electron потерял поддержку Win7
на версии 23 (февраль 2023), последняя поддерживающая ветка 22 EOL в октябре
2023. Tauri упирается в WebView2: последний рантайм для Win7 — 109, без
обновлений, и его установщик на Win7 спотыкается о TLS 1.2.

## Слои

1. **Патч джарников** — один раз при сборке, результат кладётся в раздачу.
   Готово: `tools/patch_jars.py`.
2. **Сервис авторизации и скинов** — `joinserver.jsp`, `checkserver.jsp`,
   отдача PNG. Позже становится бэкендом сайта аккаунтов.
   Готово: `auth/`.
3. **Лаунчер** — манифест сборки с хешами, докачка, запуск клиента.
   Не начат.

## Состояние патчера

`tools/patch_jars.py` переписывает константы в constant pool. Заменять можно
на строку любой длины: в class-файле константы адресуются по индексу, а не по
смещению, поэтому достаточно переписать пул и оставить остальное как есть —
ASM не нужен.

Клиентский jar подписан Mojang (`META-INF/MOJANGCS.SF`, `.RSA`), после правки
классов подпись становится недействительной. Патчер снимает её и вычищает из
`MANIFEST.MF` секции с хешами файлов — то же самое делают при установке модов
на 1.6.4. Серверный jar не подписан, там просто правка на месте.

Проверено:

- все четыре константы заменены, следов `minecraft.net` не осталось;
- патченные классы грузятся настоящим загрузчиком JVM (через `jjs` из JRE),
  `ClassFormatError` нет;
- патченный сервер стартует и останавливается штатно: 17 плагинов,
  ноль SEVERE, код выхода 0.

Боевой `spigot-1.6.4-R2.1.jar` в репозитории **не тронут** — патчить его имеет
смысл только когда появится сервис авторизации.

## Решение: раздаём готовую сборку

Рассматривались два варианта: лаунчер качает ванильный клиент у Mojang и
патчит его на машине игрока, либо мы раздаём уже готовый.

**Выбран второй.** Причина — доступность: Mojang может в любой момент
перестать раздавать легаси-версии, ровно как исчезли официальные сборки
CraftBukkit после DMCA и как сейчас доживают зеркала, с которых мы брали
ядро и Towny.

Следствие, которое легко упустить: рискует не один файл, а весь набор запуска,
и он лежит на трёх разных хостах Mojang.

| Компонент | Файлов | Объём | Хост |
|---|---|---|---|
| Клиент | 1 | 4,75 МБ | `launcher.mojang.com` |
| Библиотеки (LWJGL и пр.) | 18 | 7,78 МБ | `libraries.minecraft.net` |
| Нативы под все ОС | 7 | 2,33 МБ | `libraries.minecraft.net` |
| Ассеты (индекс `legacy`) | — | 153,48 МБ | `resources.download.minecraft.net` |
| | | **~168 МБ** | |

Ассеты — 90% веса. Без них и без библиотек пропатченный клиент не стартует,
так что зеркалировать надо весь набор.

Раз лаунчер и так раздаёт сборку со своего хоста, игрок к Mojang не ходит
вообще, и его исчезновение перестаёт что-либо значить.

### Зеркало: сделано

`tools/fetch_client.py` собирает набор по закреплённым манифестам из `client/`
и складывает в `mirror/` (в git не попадает). Раскладка каноническая —
`versions/`, `libraries/`, `assets/objects/` — чтобы отдать её лаунчеру
без переупаковки.

Итог: **623 файла, 126,19 МБ**, все sha1 сверены с манифестом Mojang.
Меньше заявленных 168 МБ, потому что ассеты адресуются по содержимому:
1120 имён указывают на 596 уникальных объектов. Дубли — легаси-алиасы
звуков, `music/calm1.ogg` и `sounds/music/game/calm1.ogg` это один файл.

На новой машине достаточно скопировать репозиторий и запустить скрипт:
он докачает недостающее и пропустит имеющееся. Если раздача Mojang умрёт,
печатается список с путём, типом, sha1, размером и исходной ссылкой —
файлы кладутся вручную, `--check` их сверит. Проверено на подмене:
битые находятся, докачиваются точечно, остальные не трогаются.

> Ассеты 1.6.4 — индекс `legacy`. Игре нужна не только папка `objects`,
> но и раскладка `assets/virtual/legacy/<имя>`: 1120 имён копируются
> из хранилища по хешу. Это задача лаунчера при подготовке профиля.

### Где хранить

- **Репозиторий** — манифесты (`1.6.4.json`, индекс ассетов), патчер,
  список хешей. Текст, диффится, весит копейки.
- **GitHub Releases / свой хост** — сами байты, ~168 МБ. В git их лить нельзя:
  ассеты никогда не меняются, но осядут в истории навсегда и утяжелят каждый
  клон.

Ванильный клиент берётся отсюда, sha1 сверяется с манифестом Mojang —
это же и доказательство происхождения:

```
https://launcher.mojang.com/v1/objects/1703704407101cf72bd88e68579e3696ce733ecd/client.jar
sha1 1703704407101cf72bd88e68579e3696ce733ecd, 4 745 096 байт
```

Оригинал храним рядом с пропатченным: при добавлении модов патч
пересобирается от ванильного клиента, а не поверх предыдущего результата.

## Сервис авторизации: сделано

`auth/` — FastAPI на SQLite, отдельный контейнер в `docker-compose.yml`,
порт 8080. Позже он же становится бэкендом сайта аккаунтов.

Протокол сверен по байткоду, а не по описаниям:

| Кто | Класс | Что делает с ответом |
|---|---|---|
| клиент | `bcw` | читает первую строку `joinserver.jsp`, сравнивает с `ok` через `equalsIgnoreCase` |
| сервер | `ThreadLoginVerifier` | читает первую строку `checkserver.jsp`, сравнивает с `YES` через `equals` |

Рукопожатие целиком:

1. Лаунчер: `POST /api/login` → session-токен.
2. Клиент стартует с `--username <ник> --session <токен>`.
3. Клиент дёргает `joinserver.jsp?user&sessionId&serverId` — проверяем токен,
   запоминаем пару (ник, serverId) на 60 секунд.
4. Сервер дёргает `checkserver.jsp?user&serverId` — сверяем пару и отвечаем
   `YES`. Рукопожатие одноразовое, запись сразу удаляется.

### Эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/login` | вход, выдача сессии |
| POST | `/api/password` | смена пароля, сбрасывает все сессии |
| POST | `/api/skin` | загрузка скина (PNG 64×32 или 64×64, до 64 КБ) |
| GET | `/game/joinserver.jsp` | легаси: клиент заходит на сервер |
| GET | `/game/checkserver.jsp` | легаси: сервер проверяет игрока |
| GET | `/MinecraftSkins/<ник>.png` | скин, 404 если нет — клиент возьмёт стандартный |
| GET | `/MinecraftCloaks/<ник>.png` | плащ |
| GET | `/healthz` | для healthcheck |

### Аккаунты

При первом старте создаётся `flower` с правами администратора. Пароль берётся
из `WF_ADMIN_PASSWORD`, по умолчанию совпадает с ником — это удобно для
разработки и небезопасно на публичном хосте. Если пароль равен нику, ответ
на вход содержит `must_change_password: true`, и сервис пишет предупреждение
в лог при старте. Проверка живая: вернёте пароль обратно — флаг вернётся.

Пароли хранятся bcrypt-хешами. На неизвестный ник и на неверный пароль ответ
одинаковый, чтобы нельзя было перебором узнать существующие аккаунты.

### Проверено

`auth/smoke_test.py` — 18 проверок, только стандартная библиотека:

```
python auth/smoke_test.py --base http://127.0.0.1:8080
```

Покрыты вход и отказы, всё рукопожатие, одноразовость, подделка сессии,
чужой serverId, загрузка и отдача скина, регистр ника, отказ без сессии.
Тест идемпотентен, гоняется повторно без сброса состояния.

Ошибка, которую он поймал: в загрузке скина PNG разбирался до проверки
сессии, и посторонний по коду ответа узнавал, валиден ли его файл.
Порядок исправлен — сначала аутентификация.

## Настраиваемый адрес

Домена пока нет, а для тестов нужен `localhost`. Проблема в том, что адрес
живёт строковой константой внутри клиента — то есть по природе своей
неизменяемый после сборки.

**Решение: лаунчер перепатчивает клиент сам, когда адрес меняется.**

1. В раздаче лежит *базовый* клиент — ванильный, позже ванильный плюс моды.
   Он одинаковый у всех, хеш стабильный, обновляется только вместе со сборкой.
2. В лаунчере поле «адрес сервера». Значение вида `localhost:8080`
   или `w-factory.ru` — принимается хост с портом или без.
3. Перед запуском лаунчер сравнивает введённый адрес с тем, на который
   пропатчен рабочий клиент. Не совпало — пересобирает из базового.
   Это около секунды на 4,7 МБ.
4. Из одного поля выводится всё: игровой сервер `<host>:25565`,
   авторизация `http://<host>:8080`, скины оттуда же. Всё на одной машине,
   поэтому одного значения достаточно.

Для этого патчер сделан **перезапускаемым**: константа опознаётся по хвосту
пути (`/game/joinserver.jsp?user=` и остальные), а не по адресу Mojang.
Раньше он искал только оригинальные строки и во второй заход молча ничего
не находил — с настраиваемым адресом это было бы фатально. Проверено:
патч на localhost, затем перепатч на другой хост, затем тот же адрес
повторно (ничего не меняется), и дважды переписанный пул по-прежнему
грузится JVM.

Режим `--show` печатает, на какие адреса джарник смотрит сейчас.

### Отвергнутый вариант

Патчить клиент на фиксированный `127.0.0.1:<порт>` и поднимать в лаунчере
локальный прокси, который форвардит на настроенный хост. Плюс — раздача
байт в байт одинаковая у всех. Минусы перевесили: лишний слушающий сокет,
конфликт портов (порт-то тоже зашит в константу), и ещё одна деталь,
способная тихо отвалиться посреди сессии. Пересборку джарника лаунчер всё
равно должен уметь — ради модов.

### Серверная сторона

Там настройка не нужна: сервер, бэкенд и сайт живут на одной машине.
Джарник сервера патчится один раз при развёртывании на адрес контейнера
авторизации — внутри compose это `http://auth:8080` (имя сервиса),
вне Docker `http://127.0.0.1:8080`.

### Проверено на localhost: связка работает

Прогон целиком, серверная половина цепочки:

1. Поднят сервис авторизации на `127.0.0.1:8080`.
2. Копия серверного джарника пропатчена на этот адрес.
3. `online-mode=true`.
4. `tools/fake_login.js` — фейковый клиент 1.6.4 на Nashorn — прошёл вход
   целиком: 0x02 handshake, 0xFD, RSA-шифрование общего секрета, 0xFC,
   переход на AES/CFB8, 0xCD.

Результат: **сервер пустил игрока**, ответив `0x01 Login` (entityId 282,
мир `world`), и записал в лог `flower[...] logged in with entity id 282`.
Обратная проверка: тот же клиент с `MC_SKIP_JOIN=1` не обращается к
`joinserver.jsp`, и сервер отвечает `Failed to verify username!`. То есть
сервис не просто вызывается, а действительно решает, кого пускать.

Две ошибки, которые всплыли по дороге, обе в тестовом клиенте:

- Считал дайджест сессии своей реализацией и не сходился с сервером.
  Заменил на вызов `MinecraftEncryption` из самого серверного джарника
  через рефлексию — сравнивать надо одной и той же функцией.
- Читал строки протокола через `DataInputStream.readChar()`. Nashorn отдаёт
  Java-`char` как строку, `String.fromCharCode` получает `NaN`, и `serverId`
  молча собирался из нулевых символов. Отсюда и расхождение дайджеста.
  Лечится чтением через `readUnsignedShort()`.

Запуск (сервер и сервис должны быть подняты):

```
jre8/bin/jjs -scripting -cp <пропатченный-сервер.jar> tools/fake_login.js
MC_SKIP_JOIN=1 …    # обратная проверка: вход должен быть отклонён
```

После теста всё возвращено: `online-mode=false`, боевой джарник не тронут
(sha1 сходится с первым коммитом), контейнер и том сервиса убраны.

### Ещё не связано

Сервис работает сам по себе. Чтобы игра начала им пользоваться, нужно:
выбрать домен, пропатчить джарники на него, вернуть на сервере
`online-mode=true`. Пока этого нет, сервис ни к чему не подключён.

## Дальше

- Связать всё вместе: выбрать домен, пропатчить джарники на него, включить
  на сервере `online-mode=true` и проверить реальный вход клиентом.
- Зеркалирование набора запуска: скачать 168 МБ по манифесту, сверить хеши,
  сложить в архив. Пока Mojang раздаёт — это делается в один заход.
- Домен. Сейчас адреса подставляются параметрами `--auth-base` / `--skin-base`.
  После патча они зашиты в клиент, и смена домена потребует передачи новой
  сборки — выбирать нужно один раз и надолго.
- Rei's Minimap: в 1.6.4 моды ставятся инъекцией классов в клиентский jar.
  Патчер уже умеет пересобирать jar, добавить в него установку модов несложно.
- Открыто: как лаунчер обновляет сам себя, и нужен ли отдельный bootstrap.
