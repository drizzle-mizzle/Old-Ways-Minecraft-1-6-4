# План: кик из мира и самообновление

Составлен 13.09.2026, после того как заработали пропуска «один на аккаунт».
Порядок работ: **1 → A → B → C → E → D**. Кик замыкает историю с пропусками
и стоит дёшево; этап C даёт рабочее самообновление ещё до D.

## Часть 1. Кик из мира при отзыве пропуска — сделано 13.09.2026

Итог: `auth/rcon.py` + вызовы в `/api/login` и `/api/password`, ключи RCON
приводит к состоянию окружения `docker/entrypoint.sh` на каждом старте, пароль
в `.env`. Проверено на живом сервере, подробности — в `launcher-wip.md`.
Ниже — как это планировалось, для истории.

Сейчас второй вход гасит пропуск первого, но игрока, который уже в мире,
никто не выкидывает: сервер после входа сервис больше не спрашивает.
Нужен доступ к консоли сервера — RCON. Ядро его поддерживает: в `server-auth.jar`
есть строки «Exception processing rcon command».

1. **Включить RCON.** В `docker-compose.yml` прокинуть `OW_RCON_PASSWORD`,
   в `server.properties` выставить `enable-rcon=true`, `rcon.port=25575`,
   `rcon.password=…`. Порт **наружу не публиковать**: он нужен только внутри
   сети compose, где до него дотягивается контейнер `auth`.
2. **Мини-клиент.** Новый `auth/rcon.py`, ~50 строк на голых сокетах:
   пакет `[длина][id][тип][тело][2 нуля]`, тип 3 — вход по паролю, 2 — команда;
   ответ с `id = -1` значит «пароль не тот». Зависимостей не добавляем.
   Таймаут 3 секунды, любая ошибка — в лог, наружу не пробрасывается.
3. **Точки вызова.** `kick(username, reason)` дёргается там же, где гасятся
   пропуска: в `/api/login` при вытеснении и в `/api/password`. Через
   `BackgroundTasks`, чтобы вход не ждал сети. Текст игроку:
   «Вы вошли с другого устройства».
4. **Выключатель.** `OW_RCON_HOST` (по умолчанию `minecraft`), `OW_RCON_PORT`,
   `OW_RCON_PASSWORD`. Пароль не задан — кик просто выключен, остальное работает;
   так же ведёт себя dev-запуск без сервера.
5. **Проверка живьём.** Зайти в игру, войти вторым «устройством»: игрока выкинуло
   с нашим текстом, в логе сервера виден kick, в логе сервиса — ответ команды.
   Отдельно — что при выключенном RCON вход по-прежнему проходит.
6. **Документы.** README и `launcher-wip.md`: убрать из «Дальше», дописать
   в раздел про пропуска.

Риск ровно один: пароль RCON оказывается в `server.properties` внутри тома.
Держим его в env и не публикуем порт.

## Часть 2. Версии и самообновление лаунчера

### Этап A. Версия из одного места

Сейчас версия живёт в `Main.java`, `package.py` достаёт её регуляркой.
Переносим в `launcher/VERSION` — одна строка SemVer `MAJOR.MINOR.PATCH`, — и оттуда
она расходится в три места: ресурс в jar (читает `Main`), `Implementation-Version`
в `MANIFEST.MF`, `VERSIONINFO` в exe (уже пишется, Windows показывает `FileVersion`).
Сравнивать всегда кортежами: `(1, 2, 10) > (1, 2, 9)`, строками — нет.

Про автоподъём: поднимать патч на **каждой** сборке плохо — отладочные прогоны
замусорят номера. Поднимаем при сборке «на отгрузку»: `tools/publish_exe.py`
увеличивает патч на `0.0.1`, обычный `launcher/build.py` не трогает.
`--set 0.3.0` — поднять минор руками, когда изменение крупное.

### Этап B. Бэкенд знает версию

В папке отгрузки появляется подкаталог `launcher/` с `Old Ways.exe` и
`oldways-launcher.jar` (их кладёт туда `publish_exe.py`). Новый `GET /api/launcher`
отдаёт `{version, exe: {size, sha256, url}, jar: {…}}`, читая версию **из самих
файлов**: у jar — из манифеста (три строки на `zipfile`), у exe — из PE-ресурса
`RT_VERSION` (свой парсер, ~70 строк, без зависимостей; покрыть проверкой на нашем
же exe). Результат кэшируется по `mtime`, чтобы не перечитывать 23 МБ на запрос.

### Этап C. Обновление jar — основной случай

Приём, который делает всё лаконичным: **exe уже является bootstrap'ом**.
Он распаковывает рантайм и запускает `java -jar oldways-launcher.jar` — то есть
работает до всякой JVM, когда jar ещё никем не занят.

1. Лаунчер видит версию выше своей, качает jar во временный файл
   в `%LOCALAPPDATA%\Old Ways`, сверяет sha256.
2. Кладёт рядом как `oldways-launcher.new.jar` (атомарным `move`).
3. Говорит «Обновление готово, перезапускаюсь», запускает exe заново
   (путь к себе стаб передаёт лаунчеру ключом `--exe`) и выходит.
4. Стаб при старте, до запуска Java: увидел `.new` — переименовал поверх
   основного. ~20 строк в `oldways.c`.

Никаких bat-файлов, которые удаляют сами себя (антивирусы это не любят),
и никакой возни с занятым файлом. Откат: прежний jar сохраняется как `.bak`,
и если новая версия не поднялась — стаб возвращает его.

### Этап D. Обновление exe — редкий случай

Нужен, только когда меняется сам стаб или рантайм Java. Схема стандартная
(так делают WinSparkle и Squirrel): качаем новый exe в папку данных, запускаем
с `--replace "<путь к текущему>" <pid>`; он ждёт выхода старого процесса,
копирует себя на его место, запускает и удаляет временный.

Права: копирование упало с отказом — предложить «Запустить обновление от
администратора» (`ShellExecuteW` с `runas`); и это невозможно — честно сказать,
где лежит скачанный файл, чтобы игрок заменил руками. Какой случай сейчас,
отвечает манифест обновления: совпали версии стаба и рантайма — хватит jar,
иначе нужен exe.

### Этап E. Защиты вокруг обновления сборки игры

- **Один лаунчер.** `FileLock` на `launcher.lock`; второй запуск показывает окно
  первого вместо своей копии.
- **Игра запущена.** При старте игры пишем `game.pid`; перед обновлением проверяем,
  жив ли процесс (`tasklist /FI "PID eq N"`), и если да — «Закройте игру, чтобы
  обновить сборку». Плюс `AccessDeniedException` как страховка: на Windows занятый
  файл всё равно не перезапишется.
- **Права на запись.** Пробная запись в каталог данных до начала докачки; при отказе
  понятное сообщение вместо стектрейса на середине.
- **Атомарность** уже есть (`.part` + переименование + sha1), добавить только
  внятные тексты ошибок.

## Чего план не закрывает

Пока нет домена и HTTPS, обновление тянется по HTTP с проверкой только sha256:
это защищает от битой закачки, но не от подмены на враждебной сети. Появится
домен — закроется само; захочется больше — подпись файла обновления ключом сервера.

Linux — низкий приоритет, всё выше написано под Windows.
